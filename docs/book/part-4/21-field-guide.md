# 第 21 章：把技巧变成日常判断

学完API后最容易走两个极端：一种是所有东西都先转成字符串，靠异常处理兜底；另一种是处处池化、零拷贝、并行，最后没人能解释谁拥有哪块内存。好的网络程序先保证协议正确、资源有界、承诺清楚，再根据测量优化真正昂贵的步骤。

这一章给你一套今后面对新协议时可重复使用的思考顺序。它不是固定参数清单，而是帮助你提出正确问题。

## 21.1 从业务承诺倒推代码

假设明天换成“扫码枪上报工件序列号”。不要先选数组大小，而应先问：允许延迟多少？能丢吗？重复会不会触发重复入库？设备是否支持重发？如果答“绝不能丢”，继续问进程被强杀时以什么为恢复依据。没有稳定存储、重发协议或外部耐久队列，就不能靠内存参数兑现这个承诺。

随后定义 ACK：收到字节、通过解析、通过鉴权、写入内存、写入耐久日志、提交数据库还是完成业务操作？把其中一个写在协议文档里，其余都不是默认附赠。重试、超时和幂等键随这一选择设计，而不是上线出重复数据后才补。

第三步才是字节协议：明确版本、大小、类型、编码、端序、帧界限、校验和错误处理。边界应该能在有限长度与有限时间内判定。错误魔数后是断开还是重同步，取决于协议；本书KG/1选择断开，以简化验证和防止无界扫描。

最后映射到实现：连接状态放哪里，消息怎样拥有数据，队列如何等待或拒绝，异常怎样结束管道，消费者怎样取消。这样写出来的代码能从业务需求一路追溯，而不是一堆“最佳实践”碰巧放在一起。

## 21.2 面对新代码时，按所有权寻找边界

先找每个读取返回的内存是谁拥有的，再找它何时失效。对 PipeReader，借用结束边界是 AdvanceTo；对 ArrayPool，边界是 Return；对 IMemoryOwner，边界是 Dispose。`readonly`、`ReadOnlyMemory`、record、异步方法这些名字都不会改变底层生命周期。

然后找每个独立所有者由谁释放：创建者不一定是最后使用者，但责任必须可以唯一说明。若队列在取消时拒绝入队，待入队对象的所有者不能凭空消失；若把池化对象交给另一个任务，生产者就不能在finally里提前归还。

再找并发访问。一个 PipeReader 对应一个读循环，一个 PipeWriter 对应一个写循环；业务并发应通过拥有自身数据的消息和有界队列实现。用锁包住一段代码之前，先考虑是否可以把所有发送收敛到一个拥有输出管道的任务。

最后找异常路径。成功释放并不难，难的是解析失败、鉴权失败、取消、写端完成、后台处理器崩溃时仍能有界退出。你应该能从任何一个 await 画出“成功 / 取消 / 异常”三条后续路径。

## 21.3 把“优化”写成可证伪的假设

“每帧创建一个数组可能增加GC压力”是可测量假设；“池化一定更快”不是合格结论。小数组可能非常便宜，池化可能带来同步、清零和生命周期复杂性。先测每秒分配量、GC暂停与CPU，再比较总体收益。

“把多段合并再解析可能多一次复制”是事实；“所以任何ToArray都禁止”是错误规则。需要异步持有一段消息、第三方解析器只接受连续内存、或者固定小头便于校验时，一次有界复制可能显著简化正确性。KG/1的头与负载各复制16字节到小栈缓冲，就是这样的取舍。

“每条Flush会增加调用与调度成本”是潜在问题；“攒越多越快”则忽略了低流量下永远等不到批次、尾延迟、业务ACK与内存压力。批量发送必须同时有条数/字节上限和时间上限，并定义失败时影响哪一批。

“增加并发消费者可能提升吞吐”也需要约束：下游数据库是否允许，是否保持设备内顺序，共享状态是否线程安全，队列是否仍有界。没有隔离热点设备时，一个高频设备可能占满共享队列，让低频但关键的报警等不到处理。

记录优化决策时保留三项：假设、测量、代价。只留下“提升了35%”的PR描述，往往无法帮助下一位工程师判断它在另一个负载下是否仍然正确。

## 21.4 故障现场，先分层再调参数

| 现象 | 首先要看的证据 | 常见的错误动作 |
|---|---|---|
| 客户端已发送但等不到下一条ACK | 服务端游标、队列等待、输出等待、ACK序号 | 盲调TCP包大小 |
| CPU不高但连接都很慢 | 线程池队列、同步阻塞、数据库等待、背压 | 立即增加线程数 |
| 内存持续增长 | 未消费/未归还内存、总连接、队列、日志积压 | 无证据地禁用GC |
| 连接偶尔只处理第一条消息 | 一次Read多帧、examined、EOF分支 | 给每次Send加sleep |
| 消息重复入库 | 重试窗口、幂等键、原子提交 | 假定TCP可靠所以不会重复 |
| 本机快、部署慢 | TLS/日志/存储/容器限制/网络RTT及输入分布 | 拿微基准证明部署无问题 |

排障要给每一层可观察的边界。收到字节计数不等于解析成功计数，入队计数不等于持久化计数，发出ACK计数不等于设备收到ACK计数。把四者放在同一张监控图里，才能定位承诺在哪一步停止兑现。

不要把每个设备ID都作为指标标签。指标通常适合低基数维度，例如错误原因和协议版本；具体设备与序号放到受控日志和追踪上下文中。否则监控本身会变成高基数内存问题。

## 21.5 每次协议改动，最少重新解释这些事

帧格式改变时，问旧客户端怎样识别新版本，长度校验和上限是否同时改变，是否允许未知类型。负载从固定结构变成JSON时，还要加解析深度、数字范围与字符编码约束，不能因为用了文本就认为输入天然安全。

并发模型改变时，问哪个组件变成多读者/多写者，原来依赖顺序的状态是否仍然成立，取消一个任务后谁等待其他任务收尾。`Task.WhenAny`只告诉你“第一个完成”，没有替你观察剩余任务的异常或释放其资源。

持久化改变时，问ACK是否移动了时点，重试是否变多，去重键与业务数据是否在同一事务内，批量提交失败后如何分辨部分成功。这里往往比Span与数组之间的差距更影响业务正确性。

安全边界改变时，问是否从loopback进入可信边界之外，设备身份如何绑定到连接，证书如何轮换，代理目标如何限制。自定义TCP端口不会自动获得HTTP路由上的认证、请求体限制和速率限制；这些要在协议入口自行实现或在明确的前置层落实。

## 21.6 为自己安排一次循序渐进的复习

第一次复习只看第1—6章：关掉IDE，口头解释每个类型和网络方向，然后再打开源码确认。能复述名词还不够，要说明如果没有这个抽象，代码会多承担什么责任。

第二次复习看第7—12章：手画游标，故意制造半帧与多帧，解释Span/Memory借用。每个失败先写原因再修，尽量不靠加入随机延时掩盖问题。

第三次复习看第13—18章：为一个明确设备类型设计接入方案。说明你选择MQTT、HTTP、现成工业协议库或自定义Kestrel协议的理由。学习Kestrel是多一个工具，不意味着所有场景都该自造协议；现成协议的设备生态、运维能力和安全互操作性常有更大价值。

最后完成[毕业练习](20-exercises.md)。如果暂时没有数据库，可以先用一个显式声明耐久语义的本地日志原型，但必须验证刷盘、截断恢复和重复重放；只调用File.WriteAsync不能自动证明断电耐久。

## 21.7 给未来自己的十条规矩

1. TCP传字节，消息边界由应用定义。
2. 数据不足与数据非法必须分开，只有完整解析成功才提交游标。
3. 读到完成通知之前先处理剩余完整数据，剩半帧则报告截断。
4. 内存视图不转移所有权，借用不得越过释放边界。
5. 一个读者、一个写者；异步不代表可以无约束并发。
6. 每个外部长度、等待、连接和队列都需要明确边界。
7. 水位是流控机制，不是总内存封顶；examined和consumed承担不同职责。
8. Flush、网络传输、业务ACK、耐久提交是不同承诺。
9. 超时与断开带来结果不确定，重试必须与幂等共同设计。
10. 先写能验证的正确性，再测真实瓶颈，最后决定是否值得增加优化复杂度。

当你能把这些规矩映射到具体代码、测试和业务代价时，就有能力继续研究更复杂的协议与更大规模的连接，而不再只能照着示例运行。
