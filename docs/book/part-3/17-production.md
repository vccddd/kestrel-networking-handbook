# 第十七章　从教学基线走向生产：定义故障后的结果

把程序运行起来，回答的是正常路径能否完成；把网关投入生产，还要回答断电、重启、重复发送、过载和证书失效之后，数据与权限处于什么状态。本章以 KG/1 为教学起点，给出生产设计的方法。除明确引用已有源码的行为外，以下持久化、幂等、身份和停机流程均为**生产蓝图，尚未由教学样例实现**。

所有实验仍只运行本机模拟器。工业网关需要现场网络、设备供应商、工艺负责人及运维团队共同评估；本书不通过真实控制命令来验证通信代码。

## 17.1 用故障时间线选择 ACK 点

当前 [GatewayConnectionHandler](../../../samples/IndustrialGateway/GatewayConnectionHandler.cs) 的顺序是读完整帧、入 Channel、序列化 ACK、Flush；[消费者](../../../samples/IndustrialGateway/TelemetryQueue.cs) 只执行日志工作。这意味着进程在入队后崩溃，数据仍可能丢失，即使 ACK 已被设备接收。

先画出生产期望的时间线：`收到 → 校验 → 耐久接收日志提交 → ACK → 下游处理 → 完成标记`。如果 ACK 定义为“耐久接收”，就必须先完成对应耐久保证再发送。一次异步文件 Write 返回、操作系统页缓存接收和满足断电恢复要求的提交并不相同；所选文件系统、数据库、磁盘缓存和同步策略都影响真正的保证。数据库提交也需要明确是单机日志提交还是副本法定人数确认。

耐久接收与业务处理是两个阶段。若收到 ACK 就表示数据库业务已经完成，延迟较高且耦合更强；若 ACK 表示网关已耐久接管，网关就必须负责之后的重试、积压容量和恢复。两种设计都可以成立，关键是客户端删除本地缓存之前，双方对承诺完全一致。不要用一个没有定义的“可靠 ACK”覆盖所有阶段。

即便先持久化再 ACK，也会存在“持久化成功但 ACK 丢失”的窗口。设备重发无法避免，服务器必须能识别重复。网络链路上没有靠“只发送一次”就自然得到的端到端恰好一次执行；可靠系统通常通过重试、幂等和事务边界让重复变成可控结果。

## 17.2 序号、设备重启与幂等键

KG/1 当前只有 uint64 序号，没有启动会话标识，模拟器每次运行默认又从 1 开始。服务器也没有序号校验。因此 `deviceId + sequence` 暂时不能被宣称为全球唯一幂等键。设备重启复用序号、换机复用编号、多个进程同时发送都可能冲突。

生产蓝图需要选择持久单调序号，或在协议新版本中加入经过认证的启动会话标识，然后明确去重作用域。一个候选键是“租户、可信设备身份、启动会话、序号”。身份来自认证结果，不完全相信载荷声明。去重记录需要存储足够久，覆盖设备离线缓存和重发窗口；提前过期就可能让旧消息再次产生副作用。

还要定义同一个键携带不同载荷时的行为。不能直接回 ACK 并忽略，因为这可能是设备 Bug、编号冲突或攻击。可保存原始载荷摘要，发现冲突则拒绝并审计。测量时间不能单独作为唯一键：设备时钟会回拨，多条数据也可能同毫秒产生。

如果消费动作是更新业务数据库，可以在同一事务中“插入幂等记录并修改业务数据”。若要再发到消息平台，则考虑事务 outbox：业务修改与待发送事件同事务落库，再由独立发送器重试。对方若没有幂等接口，发送后网络中断仍存在未知结果，必须设计查询、对账或人工处理路径。这里没有一条通用 `try/catch` 能替代业务协议。

## 17.3 过载不只是增加队列容量

有界队列能限制一部分内存，却不能让长期超载消失。假设每秒进入 1000 条、消费者只能处理 800 条，积压每秒增长 200 条；容量 128 只能吸收约 0.64 秒的差额。扩大到一万条只是延后饱和，还增加延迟和故障后的恢复时间。

生产容量规划至少记录稳定处理率、峰值持续时间、允许延迟、磁盘配额与恢复目标。若需要支撑两分钟相同差额，单算记录数就需 24000 条，还没计入索引、日志和重放开销。这里的算术只是最低需求，必须用真实大小和慢依赖压测校准。

按消息类型决定满载行为。状态快照可合并，计量明细和告警一般要耐久排队或明确拒收。超载拒收应尽早发生，设备采用指数退避并加随机抖动，避免恢复瞬间重连风暴。为单个设备、租户和目的服务分别设配额，防止一个异常发送者耗尽全局资源。

当前样例配置在 [Program](../../../samples/IndustrialGateway/Program.cs) 中给 Socket Transport 设置读写 16 KiB 流控水位，默认协议处理器并发名额 64、队列容量 128、帧预算 5 秒。这些是教学默认值，不能作为产线容量结论。HTTP 的最大请求体、反向代理限制或 `/health` 正常，均不能代替自定义 TCP 入口的长度、速率和期限限制。

## 17.4 让停机成为一个状态机

生产蓝图可以把运行状态定义为“启动恢复、接收、排空、停止”。启动先恢复耐久日志、加载身份与去重信息，再开放接收能力。排空时先让 readiness 不再接新流量，停止接受新业务连接，通知已有生产者截止；允许已接收任务在期限内提交；最后关闭队列写端、排空消费者并记录剩余恢复位置。

停机期限到达时，必须知道哪些数据已耐久接管、哪些仍在易失内存、哪些客户端可能未收到 ACK。不能为了让进程快速退出，把所有异常吞掉后写“优雅停机成功”。进程被强制杀死、机器断电或磁盘写满仍需靠恢复协议解决，优雅停机只是减少不确定窗口，不能成为唯一可靠性机制。

教学样例使用主机停止信号取消工作，没有完整的 drain 协议，也不保证清空内存队列。连接尾部、EOF、取消和已缓冲帧的顺序需要测试，不能用单一 ConnectionClosed 标志推断全部状态。系统实现可能在 FIN 到达时就触发连接关闭信号，而缓冲里仍有业务帧。书中只依据现有测试说明特定路径，不承诺通用双向半关闭支持。

## 17.5 时钟、权限和证书如何进入同一张设计图

遥测包含设备时间，不表示服务器应完全相信它。保存设备时间和服务器接收时间，使用单调时钟测量本地耗时，使用 UTC 时间表达跨系统事件。对未来时间、明显陈旧记录和时钟回拨分别制定规则；生产网络时间源不可达时，决定继续接收并标记质量，还是暂停特定业务。不要用本地墙钟相减计算超时，时间校准可能让结果突变。

认证说明谁连接，授权说明他能做什么。设备只可上报自己的测点；管理身份才可变更配置；维护证书与遥测证书使用不同权限。控制写入需要更严格的审批、双重确认、命令有效期、执行回执及设备侧联锁。本书基线没有控制命令，不提供让读者尝试执行器动作的练习。

TLS 生产设计应验证链、名称、用途和设备映射，落实撤销与轮换，见[上一章](15-proxy-tls.md)。私钥不能打进公开镜像，服务只获得读取自身证书与写自身数据目录的权限。管理 HTTP 端点也应置于独立访问边界。回环监听减少暴露面，但不等于已经实现应用认证；同机进程仍可能访问。

## 17.6 分阶段验证生产蓝图

先验证协议正确性，再验证资源上限，再验证故障恢复，最后才讨论吞吐优化。每个承诺都写一个可观察结果：非法长度从头部就拒绝；慢速输入在绝对期限后退出；队列满时不会无限分配；重启后耐久消息可恢复；重复键不会重复扣减；证书撤销后在约定窗口内拒绝新会话。

现有 [verify.py](../../../samples/IndustrialGateway/verify.py) 会构建并启动隔离的回环进程，覆盖分片发送、多个帧、EOF 缓冲、非法帧、滴流期限、连接配额和慢队列。它能检验基线边界，不能证明持久化、身份或生产容量。在工作目录为仓库根目录的终端运行：

```bash
python3 samples/IndustrialGateway/verify.py
```

脚本内部启动 `dotnet` 子进程时会把工作目录设为 `samples`，因此能读取样例的 [SDK 配置](../../../samples/global.json)。若你在已进入 `samples` 的终端执行，则使用 `python3 IndustrialGateway/verify.py`。脚本使用临时端口，并负责停止自己启动的进程；不需要将任何端口映射到外网。执行前仍要满足 .NET 10 与 Python 3 前置条件。不要为了通过测试禁用证书验证、提高到无限队列或移除期限，这会改变待验证的性质。

## 17.7 动手练习与参考答案

练习一：为“耐久日志已提交，但 ACK 在网络中丢失”写恢复流程。参考答案：设备保留待确认记录并重发；服务器查询耐久幂等记录，验证同键载荷一致，返回同一确认而不重复执行业务。没有去重记录时，先持久化再 ACK 仍可能重复消费。

练习二：设备重启又从序号 1 开始，服务器只用 deviceId+sequence 去重，会有什么结果？参考答案：新数据可能误判为旧数据，或旧去重记录过期后重放被当成新数据。应持久维护设备序号，或升级协议纳入可信启动会话；当前 KG/1 没有实现该机制。

练习三：假设接收 600 条/秒、处理 500 条/秒，允许峰值十秒，需要多少额外记录容量？参考答案：至少 1000 条，另加安全余量与在途记录；若长期保持这个速率差，任何有限队列最终都满。还要确认十秒排队延迟是否满足业务时效。

练习四：在基线中增加消费者延迟后强制退出，再次启动能恢复内存队列吗？参考答案：不能，Channel 不持久化。只做纸面推演即可得出结论；若实际实验，也必须只对本机教学进程操作，不能将“重启后服务健康”当成“此前数据已恢复”。
