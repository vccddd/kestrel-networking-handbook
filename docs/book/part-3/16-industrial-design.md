# 第十六章　设计一个有边界的工业遥测网关

本章把前面的 Pipe、连接处理器和协议解析组合起来。场景是模拟设备定时上报一个测量值，网关校验帧、放入有界队列并回复确认。我们只用回环网络和模拟器，不连接现场 PLC、仪表、执行器或生产控制系统。测量上报与控制命令的风险不同，不能把遥测样例扩展一个类型号就拿去控制真实设备。

## 16.1 先定义本章实际交付了什么

新样例 [IndustrialGateway](../../../samples/IndustrialGateway/Program.cs) 使用 .NET 10，默认只监听 `127.0.0.1:7810` 的自定义 TCP 协议，以及 `127.0.0.1:7812` 的 HTTP/1 健康端点。它不引用旧项目的 Redis 或 Fiddler 实现。其核心路径是：`TCP → KG/1 解码 → 有界 Channel → 日志消费者`，另一路在成功入队后回写 ACK。

这是可运行的教学基线。它没有 TLS、设备认证、持久化、幂等去重、重启恢复或强停机保证。消费者只做日志处理，ACK 仅表示记录曾进入易失内存队列。下面凡标为“生产蓝图”的设计都超出当前代码，不应拿来解释样例已经具备的能力。

为什么要先收窄目标？因为“采集成功”可以有很多定义：网卡收到字节、完整帧解码、入队、写盘、数据库提交、上行服务接受。把这些阶段混成一个成功状态，会在故障后无法判断哪些数据需要重发。我们先让一个最小阶段有精确含义，再逐步加强保证。

## 16.2 把 KG/1 当作双方签订的字节合同

[Protocol.cs](../../../samples/IndustrialGateway/Protocol.cs) 定义 KG/1。所有多字节整数使用大端序，头部固定 16 字节：

| 偏移 | 字节数 | 字段 | 约定 |
| --- | ---: | --- | --- |
| 0 | 2 | magic | `0x4B47`，ASCII 的 KG |
| 2 | 1 | version | 1 |
| 3 | 1 | type | 1 为 Telemetry，2 为 Ack |
| 4 | 4 | payloadLength | uint32，只计算载荷 |
| 8 | 8 | sequence | uint64，请求与对应 ACK 相同 |

Telemetry 的载荷严格是 16 字节：偏移 0 的 `deviceId` 是 uint32，偏移 4 的 `unixMs` 是 int64，偏移 12 的 `valueMilliUnits` 是 int32。测量值 23500 表示 23.500 个业务单位，负数保留符号；具体温度、压力或其他单位仍由业务约定。Ack 没有载荷，长度为零，总共 16 字节。

全局最大载荷为 4096 字节，并不表示 Telemetry 可以发 4096 字节。解析器先检查上限，再检查该类型必须为 16。这样既拒绝攻击者声称的超大长度，也拒绝类型与长度不一致的报文。版本、类型和 magic 非法时直接关闭，不扫描后续字节重同步；不完整帧等更多字节，EOF 时仍残缺则属于截断错误。

`sequence` 只是传输字段，当前样例不要求递增、不去重、不验证重放。`deviceId` 也只是未经认证的载荷字段，不代表可信设备身份。时间戳可以是任意 int64；解码成功不等于时间合理。生产蓝图需要新增业务验证，但不能让读者误以为这些字段已被安全校验。

## 16.3 从解码器看内存所有权

`TryReadTelemetry` 的三种结果很明确：false 表示不完整、异常表示非法、true 表示得到一个完整值。它先把 16 字节头复制到栈内存，再验证字段；载荷足够后复制固定 16 字节并解码。成功才推进传入序列，失败或不完整时保持序列不变。这里的两次固定小复制让跨段读取更直接，并不需要为了读取头部把整个网络缓冲 `ToArray()`。

输出 `Telemetry` 是由整数构成的值对象，不引用 Pipe 内存。因此 [GatewayConnectionHandler](../../../samples/IndustrialGateway/GatewayConnectionHandler.cs) 可以先 `AdvanceTo` 释放输入，再把该对象放入后台队列。若输出换成 `ReadOnlySequence<byte>` 切片，这个顺序就不再安全，必须在推进前复制或转移具有所有权的内存。

`ReadOneAsync` 每次只返回一帧。若一次读含三帧，它消费第一帧后将 examined 设为 consumed，表明后面两帧尚未检查；下一次调用可立即看到已有缓冲。若 examined 错设为整个缓冲末尾，Pipe 可能等待新数据，造成“明明后面还有完整帧却卡住”。正常 EOF 也可能和完整缓冲一起到来，先处理完整帧，再判断尾部是否残缺，不能一见完成标记就丢弃所有数据。

## 16.4 为什么需要有界 Channel

[TelemetryQueue](../../../samples/IndustrialGateway/TelemetryQueue.cs) 默认容量 128，单消费者、多生产者，满时采用 `BoundedChannelFullMode.Wait`。当消费者变慢，生产者的入队异步等待；同一连接不再继续无节制解析，ACK 也延后，压力最终传回客户端。这里的 `await` 不占一个线程睡等，但仍占连接、内存及超时预算，所以异步不是无限资源。

队列容量约束排队中的记录数，不是进程内存的精确上限。消费者已经取出的记录、正在等待入队的每连接记录、传输缓冲、操作系统套接字缓冲都在队列之外。样例另外为协议处理器设置默认 64 个并发处理名额，传输读写水位各 16 KiB。名额由处理器入口的共享计数器控制，不覆盖 HTTP 健康端点、操作系统接受队列，以及进入处理器前已产生的瞬时连接资源；它不是整个进程的 TCP 连接硬上限。这些传输水位用于流控，也非严格的总内存封顶。要估算总资源，必须把各层同时计算；生产部署若需要进程级硬限制，还需结合监听策略、网络入口、操作系统和部署资源约束。

生产蓝图的满队列策略取决于数据语义。周期快照可以按设备合并，只保留最新值，但必须记录被替换数量；离散告警和计量明细通常不能静默丢弃，应等待、拒绝或先持久化。`DropOldest`、`DropWrite` 之类策略会改变成功写入 API 的含义，不能沿用“入队成功等于这条记录会被处理”的解释。需要给设备明确的过载状态、重试间隔和去重规则。

## 16.5 一帧的期限与 ACK 的含义

样例默认给每帧 5000 毫秒绝对预算，覆盖完整读取、队列等待和 ACK Flush。计时从准备读取下一帧时开始，也包括等待第一个字节，所以设备上报间隔超过五秒时，空闲连接也可能被关闭；需要按自己的上报周期重新评估期限，而不是把它误认为只限制慢半包。每收到一个新字节不会重新计时，因此慢速滴流不能无限占用连接。若把期限只设为相邻字节的空闲时间，攻击者在每次到期前发一个字节就可长期占位。

当前样例在入队完成后发送 ACK，不等待消费者完成；入队后的消费与 ACK 发送可以并行，两者完成的先后并不固定。确认语义是 `volatile-memory-enqueue-only`。进程崩溃可能丢掉已经 ACK 的数据；入队后 ACK 发送失败，设备可能重试，队列中又可能出现重复。这不是矛盾，而是协议阶段与网络不确定性共同决定的结果。生产蓝图若要求断电后不丢，应让确认点落在经过定义的耐久写入之后，同时解决重复，详见[生产章](17-production.md)。

停机也同理：取消消费者并不等于清空队列。基线没有“停止接收、完成生产者、排空队列、持久化剩余项”的完整握手，不能把 Ctrl+C 视为数据不丢的证明。需要先把限制说透，才能合理安排后续工程工作。

## 16.6 动手：启动、分片和合并发送

前置条件为 .NET 10 SDK 与 Python 3。从仓库根目录先进入 `samples`，再启动服务，保持该终端运行：

```bash
cd samples
dotnet run --project IndustrialGateway/IndustrialGateway.csproj
```

SDK 选择从执行 `dotnet` 时的工作目录向上查找 [global.json](../../../samples/global.json)，不会因为 `--project` 指向某个子目录就从该项目目录开始搜索。因此在仓库根目录直接执行 `dotnet run --project samples/...` 会绕过样例的 SDK 配置，可能选到 .NET 11 等其他已安装版本；先进入 `samples` 才能按配置选择 .NET 10 SDK。也可以在这个目录运行 `dotnet --version` 核对实际选择。

在另一终端保持工作目录为仓库根目录，依次执行：

```bash
curl http://127.0.0.1:7812/health
python3 samples/IndustrialGateway/simulator.py --count 3
python3 samples/IndustrialGateway/simulator.py --count 3 --split
python3 samples/IndustrialGateway/simulator.py --count 3 --coalesce
```

[模拟器](../../../samples/IndustrialGateway/simulator.py) 会逐个校验 ACK 的 magic、版本、类型、零载荷长度及序号，并打印入易失内存的提示。`--split` 将一帧分多次发送，`--coalesce` 一次发送多个帧；它们改变客户端写入方式，不保证真实 TCP 包边界。检查每个切分位置的确定性测试在 [Checks](../../../samples/IndustrialGateway.Checks/Program.cs) 中。在第三个终端从仓库根目录进入 `samples` 后运行：

```bash
cd samples
dotnet run --project IndustrialGateway.Checks/IndustrialGateway.Checks.csproj
```

若该终端已经位于 `samples`，直接执行第二行，不要再次进入同名子目录。

健康接口应包含 `status`、`queued`、`ack`，其中 ack 为 `volatile-memory-enqueue-only`。队列通常很快被消费，看到 queued 为零是正常的，不能推断没有收到消息；消费者使用 Debug 日志，默认日志级别下未必显示每条载荷。练习结束在服务终端按 Ctrl+C，不向任何现场网段运行模拟器。

练习一：Telemetry 与 ACK 各有多少字节？参考答案：前者 16 字节头加 16 字节载荷，共 32；后者只有 16 字节头。`payloadLength=4096` 的 Telemetry 仍非法，因为类型要求严格 16。

练习二：设备收到序号 7 的 ACK 后立即让网关进程退出，能否删除设备上的原始记录？参考答案：只能依据“曾入易失队列”的约定决策，不能声称已落盘。若业务需要断电不丢，当前 ACK 不足以支持删除本地唯一副本。

练习三：收到两帧连在一起时，为什么只返回第一帧后不能把 examined 指到整个缓冲末尾？参考答案：那会谎称后续字节已经检查过，可能要求等待更多输入；应把 examined 放在本次已消费末尾，让下一帧立即可读。

练习四：设备 42 发送 deviceId 43 是否会被拒绝？参考答案：当前没有认证身份或身份绑定，不会仅因编号变化拒绝；这正是样例不能直接接生产设备的原因之一。
