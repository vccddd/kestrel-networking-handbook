# 附录 A：网络与内存术语速查

这份词典按用途组织。遇到陌生词时先看一句话，再回到对应章节，避免把名词当成彼此可以替换的东西。

## 网络与协议

| 术语 | 在本书中的含义 | 不应混淆 |
|---|---|---|
| Endpoint（端点） | 协议地址，例如IP与端口；Kestrel监听配置也称端点 | 不是一条已建立的连接 |
| TCP连接 | 两端之间的有序、可靠字节流会话 | 不提供业务消息边界，不保证业务执行一次 |
| TCP segment | 传输层分段 | 不是一次Send、一次Read或一条业务帧 |
| 业务帧 | 应用协议约定的一条完整消息的字节格式 | 可以跨多个Read、多个内存段 |
| 半帧 | 当前可用字节不够构成一条完整业务帧 | 不表示字节已经丢失 |
| 多段Sequence | 同一序列由若干不连续内存段组成 | 可以包含一条或多条完整帧，也可以只有半帧 |
| 端序 | 多字节数值中字节的排列顺序 | 与UTF-8等字符编码不同 |
| UTF-8 | 把字符编码为字节的一套规则 | 字符数量不能直接当网络字节数 |
| FIN / EOF | FIN是TCP方向结束信号；EOF是上层读取不再有输入 | 最后的ReadResult仍可能有数据 |
| RST | TCP复位，连接异常结束的一种情况 | 不等于有序读完最后业务消息 |
| TLS | 提供传输机密性、完整性和认证机制的协议 | 不自动完成业务授权、幂等和持久化 |
| WebSocket | 基于HTTP建立、具有消息语义的双向通信协议 | 映射成流时仍须遵守适配层边界 |
| CONNECT隧道 | 代理建立到目标的字节通道 | 不等于代理必然解密TLS |
| RESP | Redis序列化协议族 | 本仓库伪服务器只实现有限子集 |

## Kestrel与异步

| 术语 | 含义 | 设计上的注意 |
|---|---|---|
| ConnectionContext | Kestrel交给应用的连接上下文 | 整体生命周期归框架，不随手Dispose传入对象 |
| Transport | 应用看到的IDuplexPipe | 可被连接中间件包装并临时替换 |
| ConnectionHandler | 一条连接应用处理的终端 | 实例不保证每连接独立，字段不能随意存会话状态 |
| 连接中间件 | 接收连接上下文、可调用next的处理层 | 与HTTP请求中间件不是同一层 |
| Feature | 在上下文中保存某种能力/状态的接口对象 | 不代表已经建立线程安全或授权规则 |
| Task | 异步操作的完成凭据 | 不等于一个专属线程 |
| await | 等待异步结果，未完成时可挂起当前方法 | 不意味着被等待操作没有资源成本 |
| CancellationToken | 协作取消通知 | 不是数据库回滚或已发送字节撤回 |
| DI scope | 应用明确限定依赖实例共享与释放的范围 | 裸TCP不应假定自动有HTTP请求scope |
| singleton/scoped/transient | 同容器共享/同作用域共享/每次解析新建的注册方式 | 实际寿命还受解析与缓存方式影响 |

## 内存与Pipelines

| 术语 | 含义 | 失效/提交边界 |
|---|---|---|
| Span<T> | 连续内存范围的ref struct视图 | 不得活跃跨await；不决定底层内存在栈还是堆 |
| Memory<T> | 可保存为字段等用途的连续内存视图 | 可跨await不表示获得内存所有权 |
| ReadOnlyMemory/Sequence | 限制通过此视图写入 | 底层存储仍可能被所有者修改或复用 |
| ArrayPool | 租还数组，减少反复分配的机制 | Return后不得使用旧视图；租到的数组可能更大且含旧数据 |
| IMemoryOwner | 显式拥有并负责释放一段内存的对象 | Dispose结束本次所有权 |
| IBufferWriter | 申请可写空间并声明实际写入量的接口 | GetSpan/GetMemory后写，Advance提交数量 |
| Pipe | 单向生产者/消费者缓冲抽象 | Writer写入供Reader读取 |
| IDuplexPipe | 同一连接一侧的Input/Output接口 | 本侧Output不是本侧Input的数据源 |
| ReadOnlySequence | 可能跨多个内存段的有序数据视图 | Pipe读取返回的视图在AdvanceTo后不得继续用 |
| SequenceReader | 读取Sequence的同步游标工具 | 使用临时游标，成功才提交解析进度 |
| consumed | 之前的数据不再需要，可释放/复用 | 决定内存保留范围 |
| examined | 当前解析已经检查到的位置 | 参与下一次Read及背压进度协调 |
| FlushAsync | 按具体writer契约发布/提交数据 | 不证明对端收到、业务读取或持久化 |
| 背压 | 下游能力限制上游继续推进 | 不增加处理能力，也不等于总内存封顶 |

## 业务可靠性

**ACK** 是明确阶段的确认：TCP ACK、KG/1入队ACK、数据库提交确认的含义不同。**幂等**指重复请求不产生重复业务效果；它不代表网络只传一次。**持久化**必须说明在何种失败条件下可恢复。**WAL**是先写日志再推进状态的一类机制，耐久性取决于提交和存储策略。**Outbox**将业务修改与待发事件记录放在同一事务，再由发送器重试，仍需处理接收端重复。

**吞吐**是单位时间某阶段完成量；**延迟**是单条工作的耗时；**P99**是约99%的观测不超过的分位数，不能由平均值推出。**Counter**报告事件增量、由采集端聚合；**Gauge**报告采样时的状态。**readiness**表示可以接新业务，**liveness**表示进程还可继续运行；本实验的健康端点没有完整生产就绪检查。
