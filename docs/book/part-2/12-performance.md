# 第 12 章：验证性能，而不是背诵优化口诀

看到 Span、池化和 Pipeline，容易把它们理解成“用了就快”。真正的工业网关优化需要同时守住正确性、吞吐、尾部延迟和容量边界。一段解析器在单帧微基准里更快，却在多段输入时分配大数组，或在 EOF 时漏掉测量，就不能算完成优化。一次压测每秒处理更多请求，但队列永远在增长，也不是可持续吞吐。

本章从本仓库已经存在的实现出发，建立可以复现的测量方法。新实验目标框架为 .NET 10；旧 [KestrelFramework 项目](../../../KestrelFramework/KestrelFramework.csproj)和 [Middleware 项目](../../../KestrelApp.Middleware/KestrelApp.Middleware.csproj)为 .NET 6。比较时必须写清 SDK、运行时、构建模式和代码版本，不能把不同代际实现的结果当作单个类型带来的收益。

## 12.1 先定义值得优化的指标

吞吐是单位时间完成多少工作，必须定义“完成”：收到字节、解析完成、入队、发送 ACK、数据库持久化，是不同阶段。KG/1 实验只在入易失队列后 ACK，不能把 ACK 每秒速率称为持久化吞吐。消费者处理数量、入队数量及两者差值应同时观察。

平均延迟容易隐藏少数长等待。设备更关心从发送测量到收到匹配序号 ACK 的时间分布，至少记录 p50、p95、p99、最大值与超时数量。只统计成功请求会掩盖被拒绝、超时和断线的设备，应该报告总尝试数、成功数、错误类别及测试时间窗。队列容量越大，可能短时间成功接收更多，但尾部延迟也更高，因此不能只按成功数排名。

内存方面同时观察分配速率、GC 次数及暂停、托管堆、进程工作集、池复用后的常驻量和活动连接数。分配降低不一定使工作集降低：ArrayPool 保留数组以便复用，长连接还持有各层缓冲。CPU 高时要先确认是在字段解析、日志、序列化、加密、忙循环，还是测试客户端本身饱和，再决定优化方向。

## 12.2 先通过正确性检查，再谈快慢

新实验的 [检查程序](../../../samples/IndustrialGateway.Checks/Program.cs)覆盖不完整输入不推进、多段切分、多帧合并、非法头、长度边界、EOF、ACK 编码和满队列取消。从仓库根目录先进入 samples，再运行：

```bash
cd samples
dotnet run --project IndustrialGateway.Checks/IndustrialGateway.Checks.csproj -c Release
```

.NET SDK 根据当前工作目录向上寻找 [global.json](../../../samples/global.json)，而不是根据 `--project` 指向的目录选择。在仓库根目录直接运行可能绕过实验的 .NET 10 SDK 约束，使用本机其他主版本。本章后续实验保持 samples 为工作目录；设备模拟器的相对路径因此是 `IndustrialGateway/simulator.py`，另开终端时也应先进入 samples。

这条命令验证契约，不是性能基准。检查通过不代表所有 Socket 生命周期都覆盖，真实客户端仍要验证分批发送、半关闭、慢发送和不读取 ACK 等场景。反过来，Socket 测试通过也不能替代直接构造多段 ReadOnlySequence，因为 send 的切分不由接收端保持。

对解析优化至少保留相同测试集合：所有合法输入得到相同字段；不足时返回 false 且不推进；非法头尽早拒绝；成功只消费一帧；最后批次多帧全部处理；半帧 EOF 被识别。修改消费策略时还要观察下一次 Read 是否等待了不该等待的新数据，避免只比较解析函数返回值而遗漏调度错误。

旧 [EchoConnectionHandler](../../../KestrelApp.Middleware/Echo/EchoConnectionHandler.cs)的有符号长度和 EOF 单帧处理问题，旧 [RedisRequest](../../../KestrelApp.Middleware/Redis/RedisRequest.cs)的半包与跨段拷贝问题，都说明基准样本不能只选择正常、单段、单帧数据。正确性样本就是性能试验的边界条件，而不是测完之后的附加工作。

## 12.3 设计有实际工作的微基准

原文[相关新类型](<../../../docs/2.1 高性能buffer--相关新类型.md>)通过 `array[i] = array[i]` 与类似 Span 循环比较并得到固定排序。这种自赋值没有业务效果，JIT 的优化可能改变甚至去除工作；报告也缺少足以复现的环境信息。不能据此宣称“Span 永远快于指针，指针永远快于数组”。

更有意义的解析基准是：从预先准备的 KG/1 帧读取相同字段、累计一个可观察校验值或返回测量结果，确保每种实现做同样的验证工作。输入准备放在基准外，覆盖单段、头跨段、负载跨段和批量帧。若比较旧“整批 ToArray”与 SequenceReader，就报告不同批量长度下分配字节和耗时，不能只测最有利的一种切分。

使用 BenchmarkDotNet 时应采用 Release、独立进程、多次迭代和预热，避免调试器干扰。输出至少包含运行时版本、CPU、操作系统、GC 模式、参数、均值和分布误差；有分配差异时启用内存诊断。不要在基准内打印每帧日志，因为那主要在测日志，不是在测解析。也不要只用一个常量报文反复读取、让编译器可以推断掉工作，应让结果被框架消费并检查逻辑相同。

微基准回答局部成本，不能直接预测多连接网关吞吐。实际服务器还有 Socket 调度、管道唤醒、入队、消费者、日志和设备等待；解析优化如果只占总 CPU 的很小比例，整体收益自然有限。可以先做 CPU 采样确定热点，再决定是否值得增加更难维护的快速路径。

## 12.4 池、栈与数组没有固定分界线

原文[封装与扩展](<../../../docs/2.2 高性能buffer--封装与扩展.md>)把 1 KiB 当成 new 与 Rent 的性能分界。这是特定测试与环境下的观察，不能写成普遍选择规则。池命中、线程数、清零、对象寿命、CPU 缓存和并发竞争都会改变成本。new 数组有清零成本，池数组也有租还和潜在保留成本；低频小对象可能直接 new 更清楚，高频大缓冲可能池化更合适。

stackalloc 适合确定且很小的同步临时区域，不应把客户端声明的任意长度直接拿来分配栈。KG/1 使用固定 16 字节头和 16 字节负载，是受协议约束的小空间；若以后负载变大，应该重新设计，不能仅把常量换成 payloadLength。循环中反复 stackalloc 也需要谨慎，最好让每次同步函数调用的栈生命周期清楚，避免累计栈使用。

[ArrayPoolBufferWriter](../../../KestrelFramework/System.Buffers/ArrayPoolBufferWriter.cs)扩容会复制已写数据，它的 WrittenMemory 也不能在 Dispose 后使用。比较池化前后时，应把正常归还、异常路径归还、清理敏感内容和扩容都算在内。若测试只测 Rent、不测 Return 或清零，却用来证明整个处理路径更快，就不公平。不要以少分配为理由移除必要的生命周期边界。

## 12.5 识别复制发生在哪里

复制并不只有“有”与“没有”。旧 Redis 多段路径 ToArray 复制整批；随后每个参数又 ToArray。新 KG/1 解析只把固定小区域复制到栈上，测量结果成为独立数值；编码 ACK 则直接填写 writer 提供的区域。后者消除了每帧中间数组，却仍有网络栈与底层传输需要完成的操作。

当报文很小，固定 32 字节复制可能比复杂的逐字段多段分支更容易优化和审查。只有在真实热点中测到收益后，才考虑连续段快速路径、逐字段 SequenceReader、减少头部重复解析等改动。快速路径必须有多段回退，并且执行同样的长度与版本验证。不能让“快路径少检查”成为性能提升来源。

异步队列边界上的一次复制有时是正确代价：它换取独立所有权，使读缓冲尽快归还。对于本实验的标量测量，直接保存数值更简单；对于必须保存原报文的审计场景，应限制原始数据大小并明确释放。所谓零复制不能跨过 AdvanceTo 后还继续访问借用内存，这种行为即使在短测试中结果稳定，也属于错误。

## 12.6 端到端试验必须让积压显形

启动 [网关程序](../../../samples/IndustrialGateway/Program.cs)后，用现有 [设备模拟器](../../../samples/IndustrialGateway/simulator.py)检查默认逐帧等待 ACK、`--split` 逐字节发送和 `--coalesce` 批量发送。它是协议功能工具，没有内置多设备调度、固定到达速率或延迟分位数统计；不要把它的总运行时间当成完善压测结果。若要提高负载，需要在客户端实现受限并发并记录测量，或者启动数量受控的独立客户端。先建立正常消费者基线，再通过 Gateway 配置里的 ConsumerDelayMilliseconds 人为变慢消费，观察队列、等待和 5 秒帧预算。参数应随每次结果一同记录，不能用不同日志级别或消费者延迟直接比较实现优劣。

吞吐测试可以采用固定总量加排空阶段，也可以采用固定到达速率；两者回答的问题不同。若客户端必须收到 ACK 才发下一条，负载会随服务端变慢而自动下降，可能掩盖真实到达速率下的积压。若客户端持续并发发送，则必须限制在途数量，避免客户端本身成为无界缓冲。报告应说明模型，而不是只给“每秒多少条”。

只计算测量发送结束时的吞吐可能把尚在队列中的工作算成完成。应同时记录客户端 ACK 数、服务端入队数和处理数，并等待或明确记录剩余积压。由于 ACK 是易失入队确认，服务重启和未排空队列的丢失本来就在语义边界内；不能借压测结果声称系统提供可靠交付。

对输出慢读也要测试：设备发送很多帧却不读取 ACK，服务端输出会积压，Flush 可能等待甚至超时。不能让服务端在等待 Flush 的同时无限创建下一条 ACK。输入慢发则测试绝对帧预算是否会被每个新字节重置；正确行为应受到整帧预算约束。

## 12.7 用证据决定改动是否保留

每次只改变一个主要因素，保存基线和候选版本，重复相同负载。若差异小于测量噪声，就保留更清楚的实现。若尾部延迟改善但吞吐下降，应结合设备时限决定；若吞吐改善却增加内存到超出部署预算，也不能只报好看的指标。正式报告应该写明观察和解释之间的边界，不给未执行的测试填写推测数字。

工具可以使用 dotnet-counters 观察运行时和应用 Meter，使用 dotnet-trace 或平台分析器定位 CPU 和分配热点；工具版本与运行时需兼容。实验 [TelemetryQueue](../../../samples/IndustrialGateway/TelemetryQueue.cs)定义了入队、处理、协议错误、超时、拒绝和活动连接指标。当前指标不等于完整生产监控，若需 p99 入队等待或持久化耗时，应在对应阶段添加直方图，不能从计数器倒推出并不存在的延迟数据。

## 12.8 动手练习与参考答案

练习一：候选实现分配下降 80%，但工作集略升，是否自相矛盾？参考答案：不矛盾，池可能保留容量，进程还有非托管与内核相关开销。需要同时看稳态、峰值、池预热和活动连接，不能只用分配量代表总内存。

练习二：压测 ACK 吞吐上升，队列深度却一直增长，可以认定可持续处理能力上升吗？参考答案：不能。它可能只是更快把任务移进易失队列；应比较处理速率并包含排空时间、延迟和失败数。

练习三：为了变快，删掉版本检查与最大长度判断，微基准提升了，是否值得合入？参考答案：不是等价实现的比较。它改变了协议和容量保护，应恢复相同验证，再比较实现成本。

练习四：新循环在只读到半帧时 CPU 满载，应先池化还是检查推进？参考答案：先检查 consumed/examined 是否都停在起点，导致同一缓冲立即返回。正确性错误造成的忙循环通常比微小分配更严重。

性能选择必须建立在 [Memory 租期规则](https://learn.microsoft.com/en-us/dotnet/standard/memory-and-spans/memory-t-usage-guidelines)与 [Pipelines 读写契约](https://learn.microsoft.com/en-us/dotnet/standard/io/pipelines)之上；这些契约不能为基准成绩让步。
