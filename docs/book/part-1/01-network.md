# 第 1 章 从一条温度数据认识网络

本章要解决的问题是：设备明明发送了一条温度，服务器为什么不能“读一次、转字符串、保存”？读完后，你应能区分地址、连接、字节和业务消息，画出一条采集数据的路径，并解释为什么接收端必须分帧。只需会运行命令、读懂变量和循环；尚不需要理解缓冲池。

## 1.1 先看业务，再看网络名词

假设车间的温度采集器每秒上报一次读数。网关负责接收，后台负责存储，操作员从看板查看。采集器也许是单片机，也许是连接 PLC 的边缘程序；本书用 Python 模拟器扮演它。它们之间传的不是 C# 对象，而是双方预先约定的一串字节。

设备知道“25.125 摄氏度”，网络只知道 `0x00`、`0x01` 这样的八位数。发送端必须把设备编号、采集时间和测量值编码；接收端必须按相同约定解码。单位、符号和字段顺序都属于协议的一部分。若发送端把 25125 理解为千分之一摄氏度，接收端却当成摄氏度，网络可以完全正常，业务数据仍会错一千倍。

本书新实验称为 KG/1。设备主动建立 TCP 连接，把 Telemetry 帧发送给网关；网关校验、解析，把数据放入有界内存队列，然后发送 Ack。后台消费者从队列取数据。**Ack 只承诺已经入易失内存队列**：此时进程崩溃仍可能丢数据，不能向设备宣称“已经落库”。把承诺写清楚，是协议设计的第一步。

## 1.2 地址告诉数据去哪，端口告诉它找谁

IP 地址标识一个网络接口可以到达的位置，端口用于区分该位置上的服务。`127.0.0.1` 是 IPv4 环回地址，流量留在本机；它便于学习时隔离外部网络。`7810` 是本书为设备 TCP 服务选的端口，不是 TCP 自带的标准端口。

客户端连接 `127.0.0.1:7810`，操作系统通常替它分配一个临时本地端口，例如 `53420`。这个连接可以写成：

```text
客户端 127.0.0.1:53420  <── TCP ──>  网关 127.0.0.1:7810
```

另一台模拟设备可使用另一个临时端口连到同一个 `7810`。监听端口是接待入口，不等于只能接一个客户。反过来，同一个监听地址和端口不能随意被两个普通服务器同时占用；“地址已在使用”通常应先查已有进程，而不是修改业务解析器。

`localhost` 是名字，可能解析到 IPv4 的 `127.0.0.1`，也可能包括 IPv6 的 `::1`。本书新实验明确绑定 IPv4 环回，客户端也明确用 `127.0.0.1`，减少由地址族造成的差异。以后把服务开放到车间网络时，应重新设计绑定地址、网络访问控制和认证，不能把环回实验直接等同于设备部署。

## 1.3 TCP 保证顺序，不替应用分消息

TCP 在连接上提供有序的字节流。假设应用连续发送两条 32 字节 Telemetry 帧 A、B，接收端可能一次读到 64 字节，也可能先读到 A 的前 7 字节，再读到余下 57 字节。接收顺序保持一致；每次读取的边界由缓冲、调度和网络情况决定。

```text
发送应用： [A：32字节] [B：32字节]
读取方案一： [64字节]
读取方案二： [7字节] [20字节] [37字节]
业务结果：  都应得到 A 和 B 两条消息
```

还要分清三种不同的“分段”，它们描述的是三个维度，没有一一对应关系：

| 维度 | 谁决定边界 | 这里观察什么 |
| --- | --- | --- |
| 业务帧 | 应用协议 | 一条 KG/1 Telemetry 是否已收齐 32 字节并通过校验 |
| TCP segment（TCP 报文段） | TCP 实现根据网络与发送情况组织 | 网络如何运输字节；接收应用不靠其边界分消息 |
| Sequence 内存段 | 管道及缓冲管理 | 已收到的字节在内存中是否连续存放 |

例如，一条完整的 32 字节帧可以放在 `ReadOnlySequence<byte>` 的两个内存段中：第一段 5 字节，第二段 27 字节。它在内存中不连续，但总共已收齐，解析器应跨段读出完整帧。反过来，一块连续内存只有 16 字节时，即使它恰好容纳完整帧头，也可能只是 32 字节 Telemetry 的前半帧。**内存是否连续与消息是否完整，是两个不同问题。** 一次应用读取也可能汇集多个 TCP 报文段，不能从某次 `ReadAsync` 的结果反推出线上报文段的边界。

“半包”和“粘包”是便于交流的俗称，并不是 TCP 破坏了消息；TCP 本来就没有承诺保留应用消息边界。关掉 Nagle、调整缓冲区、每次发送后等待一下，都不能替代分帧。接收程序要能保留不足一帧的尾部，也要能从同一缓冲里继续取出后续完整帧。

一次写入成功，只能证明相应 API 接受了数据；TCP 层的确认也不证明数据库完成了事务。因此我们另设 KG/1 Ack 来表达应用进度，并且仍需定义它承诺到哪一步。发生断线时，设备可能不知道上次数据是否已入队；将来实现重传，还需要幂等键、去重和持久化策略。一个 sequence 字段本身不会自动实现这些能力。

## 1.4 帧如何把字节重新变成消息

常见分帧办法有固定长度、分隔符和长度前缀。固定长度很简单，但字段扩展困难；分隔符适合行文本，但正文含分隔符时要转义；长度前缀适合二进制消息，但必须限制长度并防止整数溢出。仓库原始 [Echo 处理者](../../../KestrelApp.Middleware/Echo/EchoConnectionHandler.cs) 使用两字节长度前缀，[Telnet 处理者](../../../KestrelApp.Middleware/Telnet/TelnetConnectionHandler.cs) 使用 `\r\n` 分隔符。

KG/1 选用 16 字节头，让接收端在拿到头后知道帧类型和负载大小。多字节整数均为大端，即高位字节先出现；这消除了机器本地字节序差异。头字段如下，offset 从零计算。

| offset | 长度 | 字段 | 约定 |
| --- | --- | --- | --- |
| 0 | 2 | magic | `0x4B47`，ASCII 为 `KG` |
| 2 | 1 | version | `1` |
| 3 | 1 | type | `1` Telemetry，`2` Ack |
| 4 | 4 | payloadLength | 无符号大端，不含头 |
| 8 | 8 | sequence | 无符号大端，请求与 Ack 对应 |

Telemetry 负载严格为 16 字节：4 字节无符号 `DeviceId`、8 字节有符号 `UnixTimeMilliseconds`、4 字节有符号 `ValueMilliUnits`，也都采用大端。因而一条合法 Telemetry 总长是 32 字节；Ack 负载长为零，总长 16 字节。值 25125 表示 25.125 个业务单位，负值也可编码。

头中声明的负载长度上限是 4096，通用帧上限由此为 4112；这不表示 Telemetry 可以带 4096 字节。解析器还必须执行“type=1 时长度必须等于 16”的类型约束。magic 便于发现发错协议的连接；version 便于明确拒绝不支持的布局；它们都不提供身份认证或加密。

## 1.5 为什么需要 Kestrel 和管道

直接使用 Socket 时，仍要处理监听、接受连接、异步读取、缓冲保留、关闭和并发。Kestrel 将这些基础能力组织成服务器和连接管道，交给应用一个 `ConnectionContext`。其中 `Transport.Input` 读设备到网关的数据，`Transport.Output` 写网关到设备的数据；两者不是本地互相回环的读写端。

缓冲区可能由多个内存段组成，所以“当前第一段不够 16 字节”不等于“所有已到数据不够头”。后面会用 `ReadOnlySequence<byte>` 和 `SequenceReader<byte>` 处理跨段。选择这些抽象的原因是让解析器表达协议规则，而不是不断搬移数组。框架降低了基础设施工作量，但不会替你决定长度上限、超时和 Ack 语义。

原文 [为什么推荐 Kestrel](<../../../docs/1.2 为什么推荐Kestrel.md>) 包含作者的技术观点与历史叙述。“更高效、更简单”不能当成本项目的性能测量。工业网关是否满足需求，应测连接数、端到端延迟、内存和故障恢复，不能只看框架名称。

## 1.6 实验：不用启动服务，也能验证字节约定

在仓库根目录运行下列命令。它只构造一帧，不建立网络连接，Python 标准库即可完成。

```bash
python3 - <<'PY'
import struct
payload = struct.pack('>Iqi', 42, 0, 25125)
frame = struct.pack('>HBBIQ', 0x4B47, 1, 1, len(payload), 7) + payload
print(len(frame))
print(frame.hex(' '))
print(struct.unpack('>HBBIQ', frame[:16]))
print(struct.unpack('>Iqi', frame[16:]))
PY
```

`>` 指定大端，`I` 是 32 位无符号数，`q` 是 64 位有符号数，`i` 是 32 位有符号数，`Q` 是 64 位无符号数。时间取零只是为了字节结果容易核对，不代表当前真实采集时间。预期帧长为 32，开头为 `4b 47 01 01 00 00 00 10`；头解码为 `(19271, 1, 1, 16, 7)`，负载解码为 `(42, 0, 25125)`。

接着在纸上把这 32 字节切为 5、11、16 字节三块。第一块不足头，应保留；第二块到达后头完整而正文未到，应继续等待；第三块到达后才能产生一条 Telemetry。若把两帧直接拼接，则应产生两条消息。把这四个观察写下来，比“本机一次读完成功”更能检查你是否理解了分帧。

## 1.7 常见错误、练习与参考答案

**错误：用浏览器打开设备端口。** 浏览器发送 HTTP 文本，KG/1 期待二进制 magic；两边协议不匹配。HTTP 健康入口是 `http://127.0.0.1:7812/health`，设备 TCP 入口是 `127.0.0.1:7810`，默认没有 7811 TLS 监听。

**错误：用字符数当长度。** 中文 UTF-8 编码通常一个字符占多个字节；本协议的长度始终以字节计。将对象转 JSON 后再数 C# 字符数，不能得到网络负载长度。

**练习一：读到 48 字节，可以断定是一条 32 字节 Telemetry 加一条 16 字节 Ack 吗？** 参考答案：不能。必须从帧头逐个验证；它也可能是一条 Telemetry 加下一条 Telemetry 的头，或者非法输入。

**练习二：已经收到 Ack，马上关机是否绝不丢数据？** 参考答案：不能保证。Ack 的承诺是易失内存入队，电源丢失或进程崩溃仍可能丢失，持久化确认需要新的协议与存储设计。

**本章交付标准：** 能独立画出设备、TCP 连接、分帧器、队列、消费者和 Ack 路径；能解释 32、16、4096、4112 四个数字的不同含义；能将相同字节流任意切块后得到相同业务消息。接下来进入 [第 2 章：仓库导览](02-repository.md)，把这些概念放到实际文件中。
